# 286 backing-store proposal: footprint and relocation review

2026-10-30; SRC-0576 / TEST-0124. This reviews the owner-supplied r4 slice C after adoption of the separate slice A and B models. It is still a proposal, not an admitted implementation or a 286 boot path. The unchanged proposal and author tests remain outside Git. The supplied header, implementation and test SHA-256 are respectively `eafa2e79e0aa75e15ab475712af6d26bab7577a6d02e2e00063ed74228a14ff7`, `87027f49ca1c01ccf357ed83df963e1071a2f0f82d568ea27fc8501c4e7c6845`, and `1814501acf6fe3f6602b9db8c497f5c271cd86c8262d8b20d60cea870038ba40`. No other AI or prohibited implementation input was used.

The pinned Open Watcom 2026-10-01 compiler in `-2 -mc -os` mode measured the proposed `cs_bg_store` at **10,880 bytes** (not including its backing memory, other owners or stack). Its two 64-entry catalogs occupy 1,536 bytes, its two 192-entry span tables 6,144, and its 192 scratch chunks 3,072; the remainder of the structure is 128 bytes in this particular ABI. The capability is 32, owner 24, and environment 32 bytes. The checked-in `scripts/Measure-PC286Store.py` verifies the pinned tools and exact proposed-header identity, then determines each size by compile-time boundaries; 133 compiler calls produced the result. It does not link or run target code. Tests confirmed it refuses a wrong header and an existing output before overwriting it. Other models, whole-program layout and stack high-water remain unmeasured.

The proposed relocation requires **all old and all new backing ranges to be disjoint simultaneously**. For a 640 KiB total conventional-memory envelope, moving B bytes this way needs at least 2B bytes of backing alone, so B cannot exceed 320 KiB even before reserved memory, the OS, metadata, alignment or fragmentation. The existing unmeasured 576 KiB cap therefore cannot describe a full 576 KiB bank set that this algorithm can relocate within that same envelope. This is a mathematical bound under the stated target, not a measurement that 320 KiB is usable or a claim that a 128 KiB Macintosh workload will fit. A 128 KiB set needs at least 256 KiB of simultaneous backing and still requires the rest of the system budget.

In a separate host-only synthetic check, an original 576 KiB map opened within a 636 KiB modeled RAM envelope; reserving the old range caused the proposed relocation to refuse for insufficient space while preserving its epoch and bound state. The contributor's own suite was also actually run in GCC x64 and Clang ASan/UBSan: each reported 1,780 fitting placements among 3,000 cases and 400 relocation properties. These are author-generated host cases, not an independent 286 run or a target performance result.

One other boundary needs an explicit contract: a failed fresh open with a null host arena leaves the store unbound and its epoch unchanged, but can already change its map, arena, RAM-envelope and catalog fields. An independently written host check observed that behavior. The draft only promises limited counters/owner preservation; do not describe the whole store as transactional without a change. The rebind-before-copy order additionally requires exclusion of all reads, new capabilities, interrupts and re-entry until copying and publication finish; generation invalidation alone cannot protect a newly opened capability during a partial copy.

Disposition: **defer slice C** until its exclusion and failure-state contracts, real target backing provider, memory/stack budgets, and an appropriate relocation strategy have been reviewed. Alternatives such as bounded staging, moving only selected banks, or refusing relocation can be evaluated against explicit workload and safety requirements; none is selected here. No implementation, physical memory discovery, target execution, paired-release input acceptance or System 1 compatibility is established.
