# Experimental Mac interrupt collection

2026-10-31; SRC-0588 / SPEC-0091 / IMPL-0102 / TEST-0135. This opt-in experiment batches the existing SCC/VIA reads and writes in one native callback while retaining the prior SCC access spacing, triple-sample checks and loss rules. It is not enabled in the normal build. The intent is to reduce callback overhead; timing improvement and working host input are not established.

The ordinary register-model suite, the fast-core version of that suite, a fast callback ordering/early-failure fixture and the existing timeline test passed with the pinned GCC toolchain. The two fast fixtures also passed under Clang AddressSanitizer and UndefinedBehaviorSanitizer. The ordering fixture models the callback; it is not an independent target-hardware observation. The original native experimental ROM passed the project's twin-build checks, used 23,568 ROM bytes, and has SHA-256 `b73b3d639db7fe93ff6c1cb1752174f5fc704c96a51f8a8f6efc7d10e9892e3d`. Inspection of the project's own linked collector showed no calls and 176 static NOPs; this count is not an independent runtime timing measurement. The rebuilt normal ROM was byte-identical to the previous candidate, SHA-256 `0ad01fe23b7a06bad000f136fae8a4a129226684b4b277aa21368eebc850dcec`. Build receipts remain in `C:\ClasSICK\mac-fast-collect-20261031-a`.

Two bounded, isolated Snow sessions booted the original experimental ROM with no disks or shared folders. The Snow log in both sessions reported an odd-address fault in our motion service shortly after boot. Inspection of our own compiled listing found a word move from an odd frame offset at the reported location. Therefore the above experimental ROM is **invalid and must not be used as a release candidate**. In the first session guarded primary-button and motion events were accepted by Windows, but capture and guest movement were not established. Neither attempt tests whether a corrected fast collector fixes the input problem. Both owned processes were externally closed and their ROM hashes remained unchanged; guest shutdown was not observed. Receipts are retained at `C:\ClasSICK\mac-fast-host-20261031-a` and `C:\ClasSICK\mac-fast-host-20261031-b`.

The corrected experiment uses separate volatile byte reads. Hosted GCC and Clang sanitizer checks passed again, including controls for a new narrow disassembly audit that rejects statically odd frame-relative word and long accesses in the motion service. The audit rejects the original faulting listing and accepts the corrected twin build; it is not a proof about dynamic addresses. The corrected original ROM has SHA-256 `47836a96ab395a3f1a8c5cee8a8de0a1679127775d9cc7e4e3d01c97b7d63732` and used 23,592 ROM bytes. In a fresh isolated 40-second Snow session with that ROM, the emulator log contained no unaligned-access or address-error report; no mouse input was tested. The owned process was externally closed and its ROM hash remained unchanged. Receipts are retained at `C:\ClasSICK\mac-fast-collect-fix-20261031-b` and `C:\ClasSICK\mac-fast-host-20261031-c`. A passing idle observation does not establish safe operation for every execution path or that mouse movement works.

In a separate 180-second isolated session of the corrected ROM, a guarded primary click changed the counter to `0001`. Two batches of eight leftward synthetic host movements each visibly moved the guest cross to the right; a following batch of downward host movements visibly moved it upward. Thus host movement reached the guest in this setup, but both observed directions were opposite the requested host movements. The attempt to begin a drag came after the session watchdog closed the window, and the process-identity guard refused every event. The session log contained no unaligned-access or address-error report. Receipts are at `C:\ClasSICK\mac-fast-host-20261031-e`; guest shutdown was not observed. This is an exploratory host observation, not a drag, human, physical or release pass, and it does not establish the direction convention on a physical Macintosh.
