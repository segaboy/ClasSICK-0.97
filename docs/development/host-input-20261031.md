# Guarded PC host input

2026-10-31; SRC-0587 / SPEC-0090 / IMPL-0101 / TEST-0134. An isolated VirtualBox session booted our original PC window candidate (EFI SHA-256 `1d8dab2888deba138a56e8b40ab23ad80dd6001abd26a82b23b26bdc2390c725`; disk SHA-256 `195bb4340e5fdba1e9fa86f5c790c00a0592b7de5941b1ef44a1505b393da37e`) with no network, sharing or reference media. Original receipts remain at `C:\ClasSICK\pc-host-drag-20261031-d`.

The host input tool positioned the exact owned window so the observed capture point lay inside its client. Its existing process, foreground, desktop, button and physical client checks remained mandatory for each event. An independently identified virtual-device input positioned the guest pointer on the title bar; [the starting framebuffer](../evidence/screenshots/2026-10-31/pc-host-before.png) is therefore an E2 setup, not host-only navigation. A guarded primary click acquired capture, and the owned-window indicator subsequently reported capture. The Windows machine had swapped buttons. A physical-left host drag moved the pointer but did not move the window; a separate primary click incremented the counter. This is an observation of this setup, not a general rule for Windows mappings.

With the default primary mapping, a guarded host down, eight rightward motions and up moved the window. Its upper border shifted from physical framebuffer x=336 to x=448, a 112-pixel difference ([after the drag](../evidence/screenshots/2026-10-31/pc-host-drag.png)). Four subsequent guarded host movements changed pixels only in the cursor region; [the window stayed in place](../evidence/screenshots/2026-10-31/pc-host-release.png). The original verification script checked the border and post-release difference. These are synthetic host GUI events, with E2 pointer setup; event receipts alone do not prove guest interpretation, and the displacement is not a per-event acceleration measurement. The owned VM was externally powered off and unregistered; the existing inventory, running states and disk roundtrip were verified unchanged. No guest shutdown is claimed.

An earlier independent isolated PC diagnostic received a guarded host movement after capture. Its original timeline recorded `18 FE 00`, with decoder states 0, 1, 2, 0, no recorded gaps or errors and the guest pointer moving from (256,171) to (254,171). Windows accepted eight host motions, which were not all represented separately in the guest report. It used a separate key marker to stop the timeline; it was not a drag test. Receipts remain at `C:\ClasSICK\pc-capture-origin-20261031-b`. A previous readiness timeout and a paused-after-capture drag attempt did not establish useful movement and are retained separately as failed controls.

This evidence establishes an automated host drag and release for this PC setup, after virtual-device positioning. It does not establish a human-input pass, unassisted host navigation, other PCs, physical hardware or System 1 compatibility. The Mac host-motion problem and paired-release qualification remain open.
