# NewPtr on the developer ROM and installed 286

Two clean Windows-native builds produced identical artifact bytes and
manifests. The installer wrote the expected 21,411,840-byte fixed disk from
scratch. All 32 generated cold starts passed, including six NewPtr runs.
Use the [build and qualification commands](disk-startup-build-20261119.md)
with BootHush `543767ae09f39d330803c05bd34311b3b3f485e53f00ec814c54c82d9c8a329f`.

It identifies each generated disk, its observed caller results, the fixture
source and the runner. The two linker warnings were the same assembly
stack-note and native-stack-segment warnings recorded in the preceding build.

The three programs in `tests/startup-new-ptr.S` load from a separate
generated disk and call the normal startup environment. Both targets
execute the same 68k instructions. None of the test instructions or result
buffers are linked into the ROM or installer. The guest writes through the
returned pointers and records results at `$9100` for external inspection.

| Guest caller | Result checked on both targets |
| --- | --- |
| Allocate and clear | Five application bytes at `$10080`, then three at `$10086`. Eight system bytes at `$A080`, then five at `$A088`. Clear variants zero the poisoned bytes and preserve earlier allocations. |
| Limits and independence | Negative and oversized requests return NIL and `memFullErr` in D0.w. The caller then requests zero bytes and the exact remaining application space. Clearing crosses the 286 bank boundary at `$18000` and preserves poisoned bytes on either side of the allocation. An exhausted application zone still permits system allocations. |
| Replace and restore | SetTrapAddress directs a NewPtr call to the guest's RAM handler. After the caller restores the original entry, the native allocator returns its first application pointer. |

The caller checks the successful and failed NZVC results with conditional
branches, verifies D0's high word on failure, and records its restored stack
pointer. It poisons `$220` with `$5A3C`, then observes `$FF94` after failure
and zero after success. Writing this word on a raw trap call is the
explicit compatibility assumption in SPEC-0146. The emulator run verifies
the implementation's behavior; it does not establish the original ROM's
behavior. The test also retains the previous startup, read error, instruction
and trap controls. These cases exercise the project's bounded startup allocator.
Disposal, compaction, movable handles, full System/Finder startup and physical
hardware qualification remain open.
