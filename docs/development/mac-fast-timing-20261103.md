# Mac fast-collector timing observations

2026-11-03; TEST-0154. The existing fast/invert-3 and opt-in WAIT-latch profiles were combined in a scratch-only diagnostic based on public revision `8ba885613b4525d116530ae55f838374714078df`. Its original MTL1 recorder was modified to retain only unstable READY passes, so the recorder can still overflow and perturbs interrupt timing. This is a diagnostic change, not an adoption of a new input rule. A second scratch build changed the per-access SCC delay from the current contract's 16 NOPs to eight and updated its experimental manifest. The published 16-NOP contract remains in force; neither short delay nor physical-hardware safety is established by these trials.

Both original diagnostic images passed the existing twin build and native checks; the 16-NOP ROM SHA-256 was `8ac46e20b92d963e3c0dc9c5a4b83e3cf42ae9bcb550ed8214e95efc5ba4b6d8`, and the eight-NOP ROM was `931f202fbeb2d50fb463289e9021af7ba1a85dd721c1b33fc79aa793ac8e88db`. All 47 recorded build-input hashes matched each scratch source tree. The only source differences between these two comparisons were the guard length and its build-script manifest description. Inspection of the actual linked collector found 176 and 88 static NOP instructions respectively; that narrow count is not an actual runtime latency or full MMIO-spacing proof. The fast and short-guard trials used isolated Snow Early128K instances, no disks or shared folders, and separately bound guarded host-input helpers. Both processes were externally stopped and both ROM hashes were unchanged; guest shutdown was not observed.

The 16-NOP run's paused record retained three unstable READY samples, no recorded overflow, after a scene-positioning click, sixteen requested upward host movements and a pause. No pre-input record was captured. The eight-NOP run's paused baseline had zero timeline entries; after positioning, sixteen requested upward movements and a pause, its record had two unstable READY samples and no recorded overflow. Its final own MWP1 record showed 28 cumulative deliveries, three cumulative losses and pointer position `(256,143)`; no baseline MWP1 was captured. Windows accepted all sixteen guarded events in each run, but capture was not verified, so that report alone does not prove guest receipt. Different elapsed times, setup and absent matching baselines make the counts unsuitable for estimating a speedup or directly comparing loss rates.

In all five retained triples the sampled B-channel DCD level differs between the second and third snapshots, which surround the collector's acknowledgement operations. This narrows the observed timing window; it does not identify individual host events, establish the number or direction of unseen transitions, or prove which physical edge caused the change. One 16-NOP triple also changes an observed second-phase bit. The [original row bytes and decoded entries](../evidence/traces/2026-11-03/mac-fast-timing.json) retain the raw evidence. Full source snapshots, the generated diagnostic ROMs, host-input receipts and closure records remain under `C:\ClasSICK\mac-fast-timeline-20261103-a`.

The eight-NOP experiment still lost input and is not a release candidate. A later recovery design must prove how it preserves event ordering and handles ambiguity across the acknowledgement before accepting any additional motion. No E1-E4, human, real-Mac or paired-release pass follows. The earlier human failures and normal Mac motion blocker remain open.

## Rejected split-recovery proposal

An original scratch proposal tried to deliver the stable pre-acknowledgement sample and defer the changed post-acknowledgement sample. The first model tests passed, but an independent review found a decisive counterexample: while a DCD latch is closed, two same-direction model steps can include a second-phase change and return, producing exactly the same visible reads as an opposite-direction bounce. The proposed code reports opposite steps in both cases and silently loses the real distinction. The lead independently executed this counterexample: the scratch proposal delivered `-1,+1` without loss, while the existing strict controller entered LOSS. The later addition of a same-button guard did not eliminate the counterexample. The proposal is rejected and was not built for or run in Snow.

The actual WAIT-latch regression now includes the hidden-cycle case for both axes, and runs against the normal and production fast collectors. Five focused GCC suites passed; normal and fast builds each passed 71 checks under Clang address and undefined-behavior sanitizers. The test rejected a compiled version of the unsafe proposal. An initial sanitizer command had a PowerShell parsing error and did not run; the corrected invocations passed. The current strict loss rule remains; these model checks do not establish a working Mac mouse.

Claude `claude-opus-5-5`, Low, reviewed a frozen 63,040-byte packet of original project source, the earlier scratch proposal, the source-informed fixture and our own trace only. Its actual normalized input SHA-256 was `6ef0d20ee6c0cc4f868ff21b43ef5f447455ec9c18925492716be5dfca018379`; the runner finished in 67.34 seconds with no tool use or executed tests. The lead reproduced the counterexample independently. Reported usage was two other input tokens, 35,410 cache-creation input tokens, 1,452 cache-read input tokens and 5,912 output tokens, with a $0.4018184 list-basis estimate; this is not a bill, quota balance or Codex savings measurement. ## Conditional pending-latch read experiment

A separate scratch-only collector retained the 16-NOP spacing but reused the first RR0 value for the second sample **only on a channel already reported pending**, relying on the source-informed model's latch remaining closed until the owned acknowledgement. Nonpending channels still receive both reads. The whole RR0 byte is reused, so the second recorded byte for a pending channel is not a second hardware observation and unrelated status bits may be stale; the current motion decision checks only DCD. The collector leaves the strict triple-sample and loss rules in place, but it changes MMIO timing and relies on a hardware-latch precondition that still needs independent target review. Twelve synthetic reference-versus-candidate scenarios passed 72 checks under GCC and Clang sanitizers; they exercised the project's latch model, not real-time hardware or other RR0 status bits. A wrong-channel reuse mutant was rejected.

The original scratch ROM built as matching twins, SHA-256 `8f4158028dab9065d652350b37e2e910015c9fc28ec27fe593980174db27db54`; all 47 recorded build inputs matched its scratch source. In one fresh isolated Snow run, its paused pre-input timeline contained zero entries. After positioning, sixteen guarded upward host movements and pause, it retained three unstable READY entries without recorded overflow. Its own final MWP1 trace showed 28 cumulative deliveries, three cumulative losses and pointer position `(256,143)`; a baseline MWP1 was not captured. Windows accepted the requested helper events; capture was unverified. The [raw rows and decoded samples](../evidence/traces/2026-11-03/mac-fast-timing.json) include this third run. The owned process was externally stopped and the ROM hash remained unchanged; no guest shutdown is claimed. These few non-time-matched trials do not prove a performance improvement, establish physical latch behavior or clear the Mac input blocker. The read-reduction proposal remains scratch-only.

## Short collector experiment and bounded drag

The combined read-reduction and shorter guard experiment is now an explicit opt-in build under SPEC-0096; ordinary builds keep the original collector and guard. Its matching native build twins have SHA-256 `1e294bab02905faf089bd1297f8670d185c84efac0c654bce558206f3fafd3ef`, exactly the scratch image run below. A default fast/invert-3 rebuild retained its earlier ROM hash `920d90bd16b204d4b159356f274273fff02c00f4a960c0cd78880c7ffb7bba1e`. The original 12-scenario model comparison exercises the actual two collector bodies; 72 checks passed under GCC and Clang address/undefined-behavior sanitizers. Six focused CTest suites passed, including existing latch, fast and WAIT cases. A wrong-channel mutant was rejected by the earlier scratch model test. These tests establish properties of the model, not real hardware timing. One first sanitizer link command omitted the inbox object and failed; the corrected command passed.

In one isolated Snow Early128K trial of that original ROM, with RelativeHw and no disks or shared folders, the paused baseline showed zero losses, pointer `(256,171)`, and window x=80. After positioning and 16 requested upward movements, the guest recorded pointer `(256,141)`, 30 cumulative deliveries and two cumulative losses. Further guarded upward movement positioned the pointer on the title bar. A held primary-button movement moved the window right, and the window stayed in place on movement after release. The final paused guest record showed pointer `(278,77)`, window x=96, 118 cumulative deliveries and 12 cumulative losses: 10 unstable and two pending. These figures include setup, pauses and movements throughout the session; there was no stage-isolated loss count for the drag. The host helper accepted its requested actions, but capture was not verified and API success alone is not guest-delivery evidence. The observed drag and guest position support the bounded result only. The process was externally stopped and the ROM hash remained unchanged; guest shutdown was not observed. [Raw record rows](../evidence/traces/2026-11-03/mac-short-collector.json) and scratch receipts under `C:\ClasSICK\mac-short-collector-20261103-a` retain the evidence.

The shortened SCC timing and pending-latch assumption have not been qualified on physical hardware, including reset-command spacing. Input was still lost, the human failures are not waived, and the Mac and PC release gates remain open. No eligible guest-only screenshot was captured in this trial.
