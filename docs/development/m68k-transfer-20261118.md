# Bounded DBcc and MOVEM execution - 2026-11-18

SPEC-0123 / IMPL-0153 / TEST-0214 adds DBcc and the admitted base-68000 MOVEM
profile to the shared bus interpreter. The corrected implementation passes
596,298 checks in each of three host profiles, 39 host suite invocations,
five native 286 cases and six native Mac cases. The 286 baseline executes
64-byte transfers across three scattered physical banks in a 128 KiB guest
address space. An independent review found one invalid-descriptor alignment
bug; the fix and a regression are included in these final results.

This is an original instruction/transport prerequisite for the selected-disk
milestone, not System/Finder startup or protected application execution.
No complete CPU, physical timing, exception restart, persistence or hardware
compatibility claim follows. The unchanged minimal `cs_m68k_step` entry point
does not gain these instructions.

The [numeric companion](m68k-transfer-20261118.json) retains the declared
source/tool identities, reports, native results, object imports, memory budgets
and local compiler frames. Full commands and generated original binaries remain
in the external report directories. No owner medium or protected program was
an input to this slice.

## Contract and implementation

SRC-0616 supplies published DBcc facts. SRC-0618 admits MOVEM facts from the
NXP-hosted Motorola *M68000 Family Programmer's Reference Manual* (1992), printed
4-128 through 4-130. The source reviewer and coordinator each checked direction,
register order, word sign extension, unchanged condition codes, original-68000
predecrement base-register behavior and postincrement base overwrite. These
are documented facts; whole-instruction atomicity is our engineering contract.
Human provenance review remains separate.

DBcc uses all sixteen CCR predicates, treating condition 1 as false for DBF.
Only the selected data register's low word decrements. The branch displacement
base is opcode PC+2, and failed target checks preserve the register frame.
MOVEM supports nonzero word/long masks and the specified base-68000 effective
addresses. PC-relative effective-address extensions follow the mask, so their
base is opcode PC+4. Loads sign-extend words; predecrement stores use original
register values, including a listed base; postincrement replaces a listed
base's loaded value with the final address. SR remains unchanged.

The maximum transfer is 16 registers / 64 bytes. Complete transfer bounds,
alignment and READ/WRITE guard checks precede operand accesses. Loads also
retain scalar READ events and stage the register frame. Stores stage all bytes
and pass the COMMIT guard before a single atomic publication. A7-derived spans
and a newly loaded A7 obey the existing explicit stack bounds. Invalid masks,
unsupported modes, callback failures and guard refusals cannot publish a partial
register frame or partial store. The zero mask is deliberately refused; this
does not assert historical architectural illegality.

`core/cpu/m68k-transfer.h` adds a wrapper containing the unchanged scalar
backend plus a synchronous atomic `write_bytes` callback. The new
`cs_m68k_bus_step_transfer` implementation remains in `m68k-bus.c`. The old
scalar backend can execute DBcc and MOVEM loads, but refuses nonzero MOVEM stores
because its scalar writes cannot provide this publication contract. The flat
path retains its prevalidated direct-pointer commit.

`cs_pc286_guest_write_bytes` validates live generation, permissions, full mapped
coverage and a nonwrapping near source span before writing. It resolves at most
64 far destination pointers, then copies with no remaining fallible operation.
`platform/pc286/m68k-transfer.[ch]` constructs the additive native descriptor
using the existing banked context admission. Guest banks exclude native
CS/DS/SS storage. No allocation, copied runtime library or flat guest-pointer
assumption was introduced. The descriptor and backing must remain stable for
each synchronous call; callbacks may not retain staging pointers or reenter.

## Verification and review correction

The independently authored host oracle exercises 73,728 DBcc combinations
through three entry points, every single-register mask, full masks, legal and
refused modes, aliases, sign extension, CCR preservation, checked target/span
arithmetic, whole-transfer guard order, final stack checks and late read/write
failure. Release, AddressSanitizer/UndefinedBehaviorSanitizer and strict C99
profiles each pass 596,298 checks. Existing startup, bus and guard suites also
pass in those profiles; the canonical harness records 39 invocations overall.

The first full `m68k-transfer-20261118-a` run passed its then-current tests.
Subsequent independent review demonstrated undefined behavior for a misaligned
wrapper: forming `&backend->scalar` preceded the alignment refusal. The retained
original reproduction exits 1 under UBSan. The corrected entry checks the
wrapper pointer and alignment before member access. The added regression checks
all misaligned offsets with fatal callback sentinels and verifies no callback,
unchanged frame, report, gateway and guest backing. The final `-b` report
supersedes `-a` for current qualification; both the earlier result and failing
reproduction remain available. No other concrete atomicity, bank, segment,
alias or guard defect was found in that review.

Shared original native fixtures check the maximum mask, DBF loop, both transfer
directions, word sign extension, listed base aliases, late failures, whole-span
WRITE and COMMIT denial and zero-mask refusal. Four independent implementation
mutants verify that the diagnostics detect the specified differences:

| Case | Expected marker | Native 286 cycles | Native Mac `-Os` cycles |
|---|---|---:|---:|

The Mac `-O0` baseline also returns `BA`, at 2,079,794 modeled cycles. The 286
wrapper additionally runs the actual banked adapter with alternating 32,767/1
byte banks, an opcode split across banks, code above 64 KiB and a 64-byte
MOVEM spanning three banks. It checks all transferred bytes and surrounding
canaries, late final-read and atomic-write refusal, stale generation, bounds,
zero/65-byte service refusal, near-source wrap, permission refusal and fresh
recovery. The companion records three inspected physical ranges with the
independent final byte oracle.

Each 286 case uses two fresh deterministic replays to cover the complete loaded
program and banked oracle within the emulator's per-run inspection limit. Their
terminal results agree exactly. This is full byte comparison across replay
groups, not a claim of one simultaneous full-memory snapshot. The loader also
poisons/clears BSS and checks the entire program checksum. Mac diagnostics are
inspected in RAM and its ROM artifact is hashed before/after; loaded ROM byte
inspection is not claimed because this pinned emulator admits RAM/video only.

The final old flat regression passes 30 host invocations, four 286 and five Mac
cases. The final old banked regression passes 36 host invocations and five 286
cases. The coordinator's routine CMake integration additionally passes 14/14
selected transfer/service/startup/bus/guard tests; that integration is separately
owned, and its copied log identity is retained in the companion.
