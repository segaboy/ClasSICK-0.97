# PC host-input corner attempt

2026-11-03; TEST-0155. A fresh isolated VirtualBox GUI session booted the existing original PC candidate disk SHA-256 `94bba3d46dac625a7d2b4a1ae58d0e775326253191503710f4b9bb00f82f35b1`, containing EFI `8e871da4e540da3f09498e3729dce55d92c9f6f95ecec464dcf6b778f0b55435`, reproduced from compiled project revision `e3cd4d867a34a72924cd7fe2693d450ca8758b64`. The session used its own disk with networking, shared folders, clipboard, drag-and-drop, USB, audio and UART disabled. The exact VM process, creation time and visible window were bound to the existing guarded input helper. The paused initial guest framebuffer is pixel-identical to the [already registered initial image](../evidence/screenshots/2026-10-31/pc-cursor15-initial.png).

After a host click, the helper's capture inspection reported the VM indicator as captured but refused its independent physical-client containment check: the Windows cursor had moved to `(2,2)`, outside the original window. The separately guarded placement-only mode moved only the owned VM window so that the captured cursor was within its client. A sequence of 32 guarded host movements of `(-8,-8)` then reported all 32 Windows events delivered. That report is not evidence of guest acceptance or exclusive capture throughout the sequence.

The [settled guest-only framebuffer](../evidence/screenshots/2026-11-03/pc-host-corner-attempt.png) did **not** show the intended top-left corner result. Decoded RGB comparison with the initial image found all changed pixels in `(503,375)-(520,392)` using exclusive right/bottom bounds, around the starting pointer. A second capture was pixel-identical to the first after-input frame. The 16-by-16 top-left cursor region did not match the [earlier device-input corner image](../evidence/screenshots/2026-11-01/pc-device-corner-top-left.png). This is a failed E3 corner observation; it does not prove why the input failed, where every intermediate guest position was, or that no movement occurred. The remaining corner sequences were not sent.

The owned VM was externally powered off and unregistered after the test. The pre-existing VM inventory and running-state lists matched, and a post-trial raw disk roundtrip matched the input hash. No guest shutdown, human input, physical hardware or paired-release qualification is claimed. Exact plans, original guest captures and helper/VM receipts remain under `C:\ClasSICK\pc-host-edges-20261103-a`.

## Captured-pointer calibration

A second fresh isolated VM used the same verified disk and guarded host-input method. After capture and positioning the owned window around the captured cursor, 64 guarded `(+8,+8)` host movements were followed by 64 guarded `(-8,-8)` movements. Windows reported all 128 events delivered. The guest framebuffer after the positive sequence was pixel-identical to the already registered [device-input bottom-right image](../evidence/screenshots/2026-11-01/pc-device-corner-bottom-right.png). After the negative sequence, the [original guest frame](../evidence/screenshots/2026-11-03/pc-host-corner-reverse.png) differed from that bottom-right image only within `(758,545)-(768,555)`; it did not reach the intended top-left corner.

The helper's coordinate receipts showed that the captured Windows cursor repeatedly returned to screen position `(2,2)` during the positive sequence; during the negative sequence it reached `(0,0)` after the first movement and subsequently remained there at guard checks. This supports host pointer clipping or capture behavior as a specific explanation for the negative-direction automation failure. It does not prove exactly how VirtualBox processes those events, prove that the guest has no bug, or qualify the remaining E3 cases. The owned VM was externally powered off and unregistered; previous VM inventory, running-state lists and raw disk roundtrip were preserved. No guest shutdown or human-input claim follows. Receipts are at `C:\ClasSICK\pc-corner-calib-20261103-b`.

## Guarded cursor-anchor experiment

A scratch-only extension to the original helper tried one cursor move to the center of the owned VM client while capture was verified. It checked process identity and hash, foreground, Default input desktop, current and destination ownership, released buttons and the current clip rectangle before moving; it rechecked ownership afterward. The selected Win32 API facts are from Microsoft's published [SetCursorPos](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setcursorpos) and [GetClipCursor](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getclipcursor) interface documentation; no example implementation was used. The project-owned guard fixture passed 115 checks under GCC and Clang sanitizers, with no native input in the fixture. A compiled mutant that removed destination ownership checking was rejected. This scratch helper is not adopted as a project tool.

In a third fresh isolated VM, the helper reported the requested and observed cursor position as `(412,298)`, and a separate capture inspection confirmed capture and containment at that time. The guest framebuffer after this positioning was pixel-identical to the initial framebuffer. The first of 64 guarded `(-8,-8)` movements was followed by the helper observing the Windows cursor at `(2,2)` again; subsequent checks found it at `(0,0)`. Windows accepted all 64 events, but the final guest framebuffer was pixel-identical to the earlier [lower-right reverse frame](../evidence/screenshots/2026-11-03/pc-host-corner-reverse.png), not the intended top-left position. This experiment shows that the one-time positioning did not hold through the sequence in this setup; it does not establish why the cursor was reset or assign a guest-driver cause. The owned VM was externally powered off and unregistered, with previous inventory, running states and the raw disk roundtrip preserved. No guest shutdown or human pass is claimed. Scratch helper and mock tests are at `C:\ClasSICK\pc-anchor-probe-20261103-a`; the trial receipts are at `C:\ClasSICK\pc-anchor-trial-20261103-c`.
