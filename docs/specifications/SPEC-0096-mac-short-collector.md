# SPEC-0096 - Experimental shorter Mac input collection

2026-11-03. This opt-in experiment builds on SPEC-0072, SPEC-0091 and the admitted interface facts SRC-0363. It is not the normal or a qualified physical-hardware profile. It may combine with SPEC-0095 and observation-only loss counts. It requires the fast collector and excludes the other behavior probes and timeline. Source-locator correction 2026-11-05: SRC-0592 describes the renderer optimization, not SCC latch evidence.

The SCC write guard uses eight NOPs and the read guard five, rather than sixteen on each access. For a channel already pending in the entry RR3 snapshot, the collector reuses its first RR0 byte as its second sample before acknowledgment. Nonpending channels retain both reads. This assumes the pending DCD latch remains closed until acknowledgment; other bits in the reused byte are not a second observation and can be stale. The existing strict ambiguity and loss rules remain in force. No unobserved direction is reconstructed.

The latch model can compare this change with the original collector, but does not establish real bus timing or hardware behavior. Timing, SCC reset-command spacing, latch behavior and complete input delivery require target qualification. An emulator drag observation is not a physical or general usability pass. Release criteria remain unchanged.

2026-11-05 amendment: in READY with a retained phase and interrupts not quiesced, ignore a direction-phase change on an axis only when its pending bit is clear and its three DCD samples all equal the retained DCD value. That axis contributes no movement. All DCD samples, buttons and moving-axis direction phases still require agreement; the existing pending consistency check remains. WAIT and PRIMING retain their prior rules. This corrects rejection caused by an unused input; it does not recover hidden steps. In the project latch model, even the original strict sampler cannot distinguish one DCD edge from three same-direction edges completed before sampling. Neither sampler has a lossless guarantee at arbitrary input rates. This limitation and all release gates remain explicit.

2026-11-05 race and diagnostic-latency correction (original engineering): in stable READY with a retained phase, no quiescence, entry RR3=0 and unchanged button, changed DCD bits may have arrived after the entry RR3 read. Read RR3 once more. Unsupported bits still fault; only an exact match to the changed axes permits EMPTY without publishing or changing retained state. Neither channel was acknowledged in this case, so its latch is left for the next finite pass. Missing/extra late pending bits, a button change, an acknowledged entry-pending channel, PRIMING and all instability keep their prior behavior. This is one additional status read on the narrow retry path, not a loop or inferred movement.

The same opt-in short profile skips unchanged foreground diagnostic copies before entering IPL7. A volatile service-count read plus a foreground dirty flag requests a copy after a service or any non-EMPTY foreground step. The service count is reread and saved inside the original exclusion; all copied fields remain coherent there. Explicit startup initializes the gate. Saturated service count falls back to copying every pass. The terminal check stays live; an interrupt racing the skip is observed next iteration. No renderer, inbox, cancellation or checkpoint rule is relaxed. Existing builder exclusions keep this profile separate from timer/checkpoint profiles. Native inspection must confirm individual longword reads and their position before exclusion. Reduced repeated masking is not a measured latency bound or proof that target losses disappear.

2026-11-05 motion-omission policy (original engineering, SHORT only): separate uncertain displacement from loss of a button/capture lifetime. In READY with retained phase, no quiescence, valid inbox/epoch/head/count/claim, and all three sampled buttons equal the retained button, an unstable motion pass or pending inconsistency may omit the whole displacement and rebaseline only the two DCD values to s3. Publish no event, leave buttons, queue, epoch and foreground drag untouched, and increment a separate saturating motion_drops counter. The clean late-latch retry takes priority. A still-closed latch may cause another omitted pass before settling. This can lose distance and does not prove chronology, arbitrary-rate losslessness or reliable button history between samples. It does not reconstruct missing movement.

A button change coincident with ambiguity, missing phase, WAIT/PRIMING, invalid inbox, queue overflow and hard fault retain the existing loss/cancellation behavior. This deliberately changes the experimental adapter's policy for motion-only ambiguity; the default strict profile and explicit inbox/capture loss contracts remain unchanged. The native MMD1 diagnostic is two uint32 words (tag 0x4D4D4431 and cumulative omitted passes), separate from MLC1 hard-loss reasons. Existing E1-E3 and human/publication limits still apply; neither worker agreement nor a passing model substitutes for target checks.

2026-11-05 observation-only addition (SRC-0596): SHORT plus LOSS_COUNTS exposes MFL1, ten uint32 words: tag0x4D464C31, non-EMPTY completions, last foreground result, last start/end VBL counters, maximum DELIVERED VBL span, last start/end producer sample counters, maximum DELIVERED sample span and DELIVERED completions. Explicit startup initializes it. Foreground reads each volatile counter separately and writes records without extending interrupt exclusion. Read only while paused; fields are not an atomic live snapshot. Source saturation makes differences lower bounds, and counter-read skew/interrupt timing prevents a physical worst-case or CPU-cycle claim. Samples count producer push attempts, including overflow, not services. No input, queue, cancellation or collector policy changes follow.

2026-11-05 extension: SPEC-0097 adds optional monotone coalescing to SHORT only, with independent MCM1 merge counts. Strict/default collector and hard-loss handling remain. See that contract for exact button/direction/claim boundaries.
